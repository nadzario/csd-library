# Проверка безопасности и критичных ошибок — 13 октября 2026

Проверены исходники `csd-library`: API, авторизация, публичные и административные
загрузки, очередь модерации, GitHub-публикация, каталог, Telegram-бот, веб-интерфейс,
скрипты импорта и настройки Docker/CI/systemd. Остальные шесть репозиториев проверены
как хранилища материалов и каталога; отдельного исполняемого приложения в них нет.
Проверка включает предыдущие исправления по трём присланным отчётам.

Ниже разделены воспроизведённые ошибки, дополнительные защитные изменения и
ограничения проверки. Публикация сайта и обновление production API проверяются
отдельно от результатов этого аудита.

## Повторная проверка присланных отчётов

- **XSS через файл `evil.pdf` с Content-Type `text/html`.** Оба файловых endpoint
  выбирают безопасный тип ответа, устанавливают `nosniff` и CSP sandbox. Админка
  выбирает режим по типу полученного Blob; PDF iframe не разрешает scripts и
  same-origin. В настоящем Chromium загруженный HTML/PDF не прочитал сессию родителя
  и не выполнил проверочный запрос утечки. Вход, предпросмотр и выход прошли.
- **Общий rate-limit за прокси.** `TRUSTED_PROXIES` явно задаёт доверенные IP/CIDR.
  Без настройки заголовки клиента не учитываются. Тест показывает отдельные лимиты
  для клиентов доверенного прокси и игнорирование поддельного X-Forwarded-For от
  прямого недоверенного соединения. Production-прокси пользователя не проверялся.
- **Запись до 2 ГБ через публичную форму с лимитом 95 МБ.** Публичный endpoint
  передаёт собственный лимит multipart-парсеру и потоковому загрузчику до записи;
  сверхлимитная заявка отвечает 413 и не попадает в очередь. Ошибки потока очищают
  частичный файл.

## Дополнительная защита

- Прокси материалов принимает только HTTPS GitHub Release Asset URLs и проверяет
  каждый redirect по разрешённым GitHub/CDN-хостам. Запрос к loopback, metadata IP,
  URL другого назначения или redirect во внутреннюю сеть отклоняется. Это защита
  от SSRF при подмене URL в каталоге; анонимный путь изменения downloadUrl не найден.
- JWT допускает только HS256; защищённые маршруты требуют role=admin.
  Действительный токен другой роли получает 403, неверные/просроченные/unsigned — 401.
- Ошибки локального каталога больше не превращаются молча в пустую библиотеку;
  стандартный путь к нему определяется относительно модуля, независимо от cwd
  npm workspace.
- Одновременное создание GitHub release bucket учитывает конфликт с другим
  процессом. Сетевые загрузки GitHub ограничены по времени, перенаправление
  авторизованного upload-запроса запрещено. Реальные записи в GitHub не выполнялись.
- Очереди заявок исключены из Git и Docker build context также при запуске API
  из workspace-каталога `apps/api`.

## Зависимости

До обновления `npm audit` сообщил 14 затронутых пакетов: 5 critical, 7 high и
2 moderate, включая fast-jwt, Fastify, multipart busboy и зависимости инструментария.
Оценки npm относятся к пакетам; они не доказывают применимость каждой advisory
к маршрутам этого приложения.

Совместимые обновления внесены в lockfile; Vitest обновлён до 5.0.4 во всех трёх
workspaces. После обновления полный `npm audit` сообщает **0 известных уязвимостей**.
Нужен поддерживаемый Node 22.12+, 24.x или 26+. Общие тесты запускаются только из
`src`, чтобы не считать повторно скомпилированные тесты из `dist`.

## Оставшиеся ограничения и действия при развёртывании

1. Очередь JSON и её лимиты рассчитаны на **один процесс API**. Для нескольких
   процессов/реплик нужны общее хранилище и межпроцессные блокировки; внутренний
   mutex и резервирование в памяти этого не обеспечивают.
2. Для Compose bind mounts владелец/права каталогов на хосте должны разрешать
   запись UID/GID 1000. `COPY --chown` не исправляет права подключённого host directory.
3. За nginx/Cloudflare задайте фактические IP/CIDR доверенных прокси и ограничьте
   доступ в обход них. Не доверяйте всей сети без необходимости.
4. Задайте уникальные секреты, права GitHub Contents и подходящую ветку
   `GITHUB_CATALOG_BRANCH`. Protected branch может запретить прямой updateRef;
   это требует настройки доступа, а не force push.
5. Реальные публикации GitHub, длительный импорт Яндекса, Telegram polling,
   GitHub Actions/Pages deployment и production ingress не запускались.
   Каталожные гонки проверены моделью Git API, а не записями в живой репозиторий.
6. Изменения кода не устраняют уже украденные токены: если старая версия была
   доступна, замените JWT_SECRET и пароль администратора перед развёртыванием.
7. Проверки аудита сами по себе не подтверждают обновление production сервера.
   Отсутствие известных advisories и прохождение этих сценариев не является
   доказательством отсутствия всех багов.

## Изменение способа публикации после аудита

По решению владельца веб-админка и публичная форма отправки полностью удалены
из исходников и Pages-сборки. Web entry point теперь открывает только каталог;
файл `admin/index.html`, компонент Admin, форма SubmitMaterial и клиент API удалены.
Pages workflow не передаёт VITE_API_URL. Контакт и работа с материалами остаются
через ссылку https://t.me/csdrive_bot; серверные компоненты сохранены для дальнейшей
разработки Telegram-бота. Production API, по сообщению владельца, не существует,
поэтому production-секреты не менялись и сервер не развёртывался.
